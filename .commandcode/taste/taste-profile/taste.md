# Taste Profile
- Strongly prefers minimal, targeted changes: no unrelated refactoring, no formatting-only changes, no speculative features, no new frameworks or dependencies added just to enable a change (work within existing stack, and document a manual verification procedure if test infra is missing). Confidence: 0.8
- Expects honest test reporting: never claim a test passed unless it was actually executed and the result observed; explicitly call out environment limitations (e.g. tests that couldn't run) as blockers. Confidence: 0.9
- Prefers concise reporting: findings, implementation decisions, test results, and remaining blockers only — no lengthy explanations or repeated full-suite runs after every edit. Confidence: 0.7
- During reviews/audits, minimize token usage: inspect only the relevant files,(e.g. start with `git status`/`git diff --stat`), use focused targeted searches (grep/background reads), and avoid dumping entire files. Confidence: 0.8
- Requires fail-safe guards for destructive operations: destructive test setup/cleanup must refuse to run unless an explicit opt-in is set, and safety judgments must not rely on database hostnames or heuristics to decide what counts as a "safe" target. Confidence: 0.8
- Never take version-control actions (commit, push, create PR) unless explicitly asked; leave changes uncommitted and report what was changed instead. Confidence: 0.85
- Never expose, request, or generate anything containing the user's credentials — passwords, database secrets, tokens, JWT secrets, etc.; the user supplies credentials via their own local method (e.g. hand-edited `.env`, system env vars), and the agent must work around needing them. Confidence: 0.85
- For database setup/migration work AND audit/review tasks, prefers read-only/verification-only behavior unless execution is explicitly requested: no file edits, no running migrations or destructive database commands; and for reports, prefers a concise prioritized list with file/line references plus a single recommended next action. Confidence: 0.75
- In audits/reviews, findings must be evidence-based: separate confirmed defects from risks that need additional tests, never speculate or report missing features as defects without code evidence, and rank by severity (Critical/High/Medium/Low). Confidence: 0.85
- When adding safety guards, they must be layered/additive (never weaken or replace an existing safeguard such as an explicit opt-in flag), and must fail before any destructive action (e.g. reject an invalid target before opening a connection or running cleanup). Always document the limits of a safeguard plainly — a naming convention is not proof of disposability/safety. Confidence: 0.85
- For validating targets/inputs (e.g. database URLs, hostnames), prefer structural validation on parsed structured fields over fragile substring matching across raw strings. Confidence: 0.8
- Considers behavior/testing claims (e.g. "concurrency-safe", "fixed") only valid when a test actually exercises that behavior against the real system — never assert safety or correctness that the executed tests don't demonstrate; state probabilistic/asserted-vs-demonstrated scope honestly. Confidence: 0.9
- When diagnosing failing tests, first classify each failure as test defect vs. genuine application defect; fix tests to match a valid production API contract (e.g. use attribute access on the actual response model) and never weaken/alter valid production code purely to satisfy a failing test, and never weaken tests or assertions to make a suite pass. If the intended contract is unclear, explain the ambiguity instead of guessing. Confidence: 0.8
- Requires narrow, precise error classification in handling logic: retry/recover only the specific identified failure (e.g. exact SQLSTATE + constraint name for a unique violation), never retry unrelated errors or database failures indiscriminately, and fix check-then-act races with a concurrency-safe mechanism (e.g. DB-backed sequence or savepoint-based retry against the DB unique constraint) that keeps surrounding transaction work intact. Confidence: 0.8
- Prefer deterministic tests over tests requiring live external services: stub/mock remote access (e.g. JWKS fetches, external APIs) with locally generated fixtures/key material so tests run without network access or real third-party credentials. Confidence: 0.85
- For tasks outside application code (e.g. CI/infra setup), never modify application code unless strictly required to make the task work, and explain any such out-of-scope change before making it. Confidence: 0.8
- When the repo has no declared convention or policy (e.g. pinned Python version, tool versions), state the gap explicitly and explain the basis for the default chosen instead of adopting one silently. Confidence: 0.75
- The website-cj project is a production deployment for a small business (5–6 users): keep solutions simple and proportionate to that scale — prefer the least-moving-parts option (e.g. env-based config allowlists over service-role keys or metadata surgery) and explicitly present heavier alternatives as non-recommended. Confidence: 0.8
- Never weaken authentication or authorization to make a task easier: don't disable auth, bypass admin guards, hardcode credentials, or broadly grant access (e.g. making every user admin), even in local/dev workflows. JWT validation must verify signatures against trusted key sources (e.g. the issuer's published JWKS), restrict accepted algorithms with an explicit allowlist, and never trust claims from an unverified token or fall back to insecure validation. Confidence: 0.85
- When the user asks for a focused security review, follow their prescribed report protocol: start with a concise audit summary classifying each requirement as `PASS`, `FIX`, or `NEEDS VERIFICATION`, make only minimal fixes with per-file explanations, run tests and report observed results, close with exact local verification steps and remaining limitations, and state plainly when no changes are needed rather than inventing work. Confidence: 0.7
